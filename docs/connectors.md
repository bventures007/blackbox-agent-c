# Connectors and the worker

Status: implemented against the provider-shaped local fixture (synthetic). No Shopify store, Shopify Payments account or merchant credentials exist in this environment, so every live row (SLICE-02, SOURCE-01 live) is `blocked_external`. Nothing below claims live provider evidence.

Code: `packages/connectors` (adapters, normalization, mapping, ingestion client), `apps/worker` (pg-boss jobs, scheduler, sync engine), `fixtures/shopify` (fixture server), `tests/worker` (vitest), `integrations/mappings/*.json` (per-capability mapping artifacts), `packages/database/migrations/0100_worker.sql` (worker tables).

## Adapter interface (`packages/connectors/src/types.ts`)

```ts
interface SourceAdapter {
  provider: string;
  capabilities: CapabilityDeclaration[];            // register row id, dataset, schedule, three mode declarations, grants, limitations, emitted families
  checkCredentials(): Promise<CredentialCheck>;     // account_ref (immutable account id), granted/missing grants, blocked capabilities, api_version
  backfill(capability_id, plan: BackfillPlan, cursor): Promise<Page>;      // one page of the plan window (+ open-items phase)
  incremental(capability_id, cursor, now): Promise<Page>;                  // one page since the persisted floor (with overlap)
  reconcile(capability_id, window, cursor): Promise<Page>;                 // one page of a bounded re-read
}
```

A `Page` carries normalized `Observation`s (`provider_event_id` account-scoped, `kind` from `packages/contracts/events.json`, `record_id`, `dataset`, `occurred_at`, `source_time`, `entity` refs, typed `payload` without PII, raw `evidence` blob, explicit `test` flag), explicit `rejected` inputs (missing required fields / unsupported shapes, never silently zero), `next_cursor`, `done`, `loaded_records`, `total_records` (only when the provider states an exact count) and the observed throttle status. Adapters never touch the database.

Ingestion client (`src/ingest.ts`): inside one tenant transaction (`SELECT set_config('app.tenant_id', $1, true)` as role `bb_worker`) each observation is checked against `deliveries` (dedupe boundary): new identity -> `journal_evidence` row + Source entry + derived entries through `append_journal_entries(jsonb)` (`input_entry_ids` = source entry, `derivation_rule = connectors.mapping.v1:<kind>-><track>`); same identity and hash -> duplicate (`attempts++`); same identity, different content -> `source.conflict_observed` entry referencing the original plus an open `review_cases` row. The batch is logged (`journal.batch_committed`) only after COMMIT.

Mapping (`src/mapping.ts`, table-driven, validated against `events.json`): order.accepted/revised/cancelled -> fact; inventory.snapshot -> fact; inventory.reserved/reservation_released -> reservation; allocation.revised -> fact; payment.authorized/voided/failed -> fact (events.json gives payments source/fact/movement, so an authorization is a fact, never a cash movement or commitment); payment.captured -> movement; payment.fee_booked -> movement; invoice.payment_marked -> fact (no cash); invoice.credit_issued -> fact + commitment; shipment.dispatched -> movement + reservation release; shipment.delivered -> fact; return.approved/revised/cancelled -> fact (returns dataset has no commitment track); return.received/restocked -> movement; refund.pending -> reservation (hold); refund.completed -> movement + reservation; payout.announced -> commitment; payout.sent -> movement (in transit); payout.failed -> fact; provider.ledger_posted -> movement; provider.balance_observed -> fact; provider.hold_* -> reservation; dispute.opened/resolved -> fact; chargeback.debit_posted/reversed -> movement; bank.credit_booked -> movement. Since the P1 integration this table (`DERIVED_TRACKS`) and the entry-draft builder `buildEntryDrafts` in `packages/connectors/src/mapping.ts` are the ONE mapping used by both the worker and the API replay/producer path (`packages/application/src/mapping` delegates to it; ADR-0007). Every family derives at least a fact; allocation.revised derives a fact only.

## Shopify authorization path (P0 feasibility, verified 2026-11-01 against shopify.dev)

- API: GraphQL Admin API, pinned version **`2026-10`** (`SHOPIFY_API_VERSION`). The versioning page lists `2026-10` as latest stable (accessible until 2027-10-16), `2026-01/04/07` stable, `2027-01` release candidate and **`2025-10` as unsupported** - so the version suggested in the brief cannot be pinned; requests for an unsupported version fall forward to the oldest stable version. Endpoint `https://{shop}.myshopify.com/admin/api/2026-10/graphql.json`, header `X-Shopify-Access-Token`.
- Token path 1 (existing apps): Admin API access token of a merchant-created custom app (Shopify admin, "Develop apps"), shown once at generation. Shopify's current documentation states that **merchants can no longer create new admin-created custom apps**; existing ones keep working.
- Token path 2 (new single-store apps, supported, no redirect): create the app in the Dev Dashboard, release a version with the read scopes, install it on the store, then obtain a token with the **client credentials grant**: `POST https://{shop}.myshopify.com/admin/oauth/access_token` with form fields `grant_type=client_credentials&client_id&client_secret`; response `access_token`, `scope`, `expires_in` (always 86399 s). Only apps and stores in the same Shopify organization may use it; other stores answer `shop_not_permitted`. The client refreshes one minute before expiry. No OAuth redirect to localhost is needed in either path. The connector accepts both (`secret.access_token` or `secret.client_id` + `secret.client_secret`).
- Scopes (recorded grants): `read_orders` (orders, transactions, refunds); `read_all_orders` approval for orders older than 60 days (the Order object documents the 60-day default); `read_products`, `read_inventory` (inventory levels); `read_fulfillments`; `read_returns`; `read_merchant_managed_fulfillment_orders` / `read_assigned_fulfillment_orders` (fulfillment orders); `read_shopify_payments_payouts` (payouts and balance transactions; the balance transaction object documents the `view_payouts` permission); `read_shopify_payments_disputes` (disputes); the Shopify Payments account object requires `read_shopify_payments` or `read_shopify_payments_accounts` and must be `activated`. `checkCredentials()` reads `currentAppInstallation.accessScopes` and marks capabilities with missing grants as blocked (`capability_health.next_check_reason = missing_grant`).
- Rate limits (verified): calculated query cost, single query max 1,000 points, restore rate 100 points/s (Standard), 200 (Advanced), 1,000 (Plus), 2,000 (Enterprise); `extensions.cost.throttleStatus { maximumAvailable, currentlyAvailable, restoreRate }`; the recommended backoff is one second. The client waits for restore before a request that would exceed the available points, honours HTTP 429 `Retry-After` (fallback 1 s) and `THROTTLED` GraphQL errors, retries 5xx with exponential backoff (max 5), and never retries 401/403.
- Not verifiable offline (recorded, to be proven at SLICE-02/SOURCE-01 with an authorized store): the exact bucket size per plan (the docs example shows 1,000), whether `balanceTransactions`/`payouts`/`disputes` accept the `processed_at`/`issued_at`/`initiated_at` query filters the adapter sends, the full `ShopifyPaymentsTransactionType` enum (the adapter maps `DISPUTE`/`DISPUTE_REVERSAL`), payout `externalTraceId`, `ReverseDelivery` availability, and the merchant's actual history depth. No merchant account change, order, charge or refund is ever created by the connector (read-only scopes only).

## Capabilities, poll groups and schedules

| Poll group | Capabilities | Provider query | Default interval (bounds, jitter) | Overlap | Reconcile |
| --- | --- | --- | --- | --- | --- |
| `shopify:orders` | shopify.orders, shopify.payments, shopify.fulfillments, shopify.refunds, shopify.returns, shopify.receipts | `orders(sortKey: UPDATED_AT)` with nested line items, transactions, fulfillments, refunds, returns + dispositions; `ordersCount` for exact totals | 300 s (60-3600 s, 30 s) | 900 s | every 6 h, 48 h window |
| `shopify:stock` | shopify.stock | `inventoryItems` -> `inventoryLevels.quantities(names: available,on_hand,committed,reserved,damaged,safety_stock,quality_control,incoming)` | 900 s (300 s-6 h, 60 s) | 900 s | daily, 24 h window |
| `shopify:allocations` | shopify.allocations | `fulfillmentOrders` (planned work; `is_stock_reservation = false`) | 900 s | 900 s | daily |
| `shopify_payments:ledger` | shopify_payments.provider_ledger, shopify_payments.refunds | `shopifyPaymentsAccount.balanceTransactions(sortKey: PROCESSED_AT)` | 1800 s (300 s-24 h, 120 s) | 3600 s | daily, 7 d window |
| `shopify_payments:payouts` | shopify_payments.payouts | `shopifyPaymentsAccount.payouts(sortKey: ISSUED_AT)` | 1800 s | 3600 s | daily |
| `shopify_payments:disputes` | shopify_payments.disputes | `shopifyPaymentsAccount.disputes` (+ DISPUTE/DISPUTE_REVERSAL ledger postings from the ledger group) | 1800 s | 3600 s | daily |
| `shopify_payments:positions` | shopify_payments.positions | `shopifyPaymentsAccount.balance` snapshot per poll | 1800 s | - | - |
| none | shopify_payments.holds | no provider object; unsupported with reason | - | - | - |
| none | generic.* (authenticated_push), bank_csv.bank (import), replay (import), policy (internal), runtime (internal) | not polled; `PollingUnsupportedError` with the reason; `next_check_reason` explains why no next poll applies | - | - | - |

Backfill (orders group): phase `window` = `created_at:>=requested_from AND created_at:<initial_cutoff`, then phase `open` (when the plan includes open items) = older orders that are `status:open` or pending/authorized/partially_paid or unshipped/partial. Strict from-now plans import nothing and seed the incremental floor at the cutoff. Incremental: `updated_at:>=floor`, floor = max(previous, min(newest updatedAt, now) - overlap). Reconcile: `updated_at` within `[to - window, to]`. Identities: `"<shop numeric id>|order:<id>|accepted"` (stable original values), `"|rev:<updatedAt>"`, `"|cancelled"`, `"|txn:<id>|<status>"`, `"|ful:<id>|dispatched|delivered|cancelled|observed:<status>"`, `"|ret:<id>|<status>"`, `"|disp:<id>|<type>"`, `"|inv:<level id>|<updatedAt>"`, `"|fo:<id>|<updatedAt>"`, `"|payout:<id>|<status>"`, `"|bt:<id>|posted|fee|refund|dispute|dispute_reversal"`, `"|dispute:<id>|<status>"`, `"|balance:<account>|<currency>|<observed_at>"`. All money is integer minor units + ISO currency (exact decimal parsing), quantities decimal strings + `piece`. `test: true` transactions/balance transactions are preserved as an explicit payload flag and are rejected by validation when absent.

Known limitations are declared per capability (`CapabilityDeclaration.limitations`) and in the mapping artifacts: 60-day order access without `read_all_orders`; only the current order revision is observable; no reservation evidence (dispatch carries `reservation_released: null`); Return/disposition objects expose no own timestamp in the pinned subset (effective time = `Order.updatedAt`, disclosed); `reverse_shipment_id`, payout `trace_reference`/`reversal_id`, dispute `original_transaction_id`, balance `processing/available/held` and all hold fields are `missing`; `payment.fee_booked` is the fee breakdown of the same ledger entry (`included_in_ledger_entry: true`), not an extra debit; shop-side refunds and ledger refunds share `economic_effect_id = shopify:transaction:<id>`.

## Worker (`apps/worker`)

Binds no listener. Entry `apps/worker/src/index.ts` (`pnpm --filter @blackbox/worker build && node apps/worker/dist/index.js`, or `pnpm --filter @blackbox/worker dev`). PostgreSQL through `DATABASE_URL_WORKER` (role `bb_worker`; `WORKER_DATABASE_URL` accepted as fallback for the database package's naming). pg-boss 12 stores jobs in schema `pgboss` (pre-created by migration 0100; pg-boss additionally issues `CREATE SCHEMA IF NOT EXISTS`, which PostgreSQL only allows with `CREATE` on the database, so 0100 grants that to `bb_worker` for its own database; verified: pg-boss schema version 46 installs 13 tables as `bb_worker`, jobs are worked, a `singleton` queue serializes jobs per key and the scheduler's dispatch lease prevents duplicate enqueues).

| Job / loop | Trigger | Behaviour |
| --- | --- | --- |
| `source.run` (pg-boss, singleton key `<connection>:<poll group>`) | scheduler tick | Executes one import run (`backfill`, `incremental`, `reconcile`, `check`) page by page with a checkpoint after every COMMIT; `MAX_PAGES_PER_JOB` pages per attempt, then re-queued with its checkpoint; retries with backoff (`JOB_RETRY_LIMIT`, default 5), dead letter queue `source.dead` plus visible `worker_dead_letters` rows and `import_runs.state = failed`. |
| scheduler tick (in-process, `SCHEDULER_TICK_MS`) | interval | Compares wall clock with monotonic time (gap >= `SUSPENSION_THRESHOLD_MS` = sleep/wake or clock change); enumerates tenants (policy `worker_enumerate` on `tenants`), then per tenant under RLS: ensures `capability_health` rows (`next_check_reason` = `no_import_plan`, `scheduled`, or the no-poll reason), picks API-created queued runs whose lease expired, creates incremental runs for due poll groups and reconciliation runs when `next_reconciliation_at` is due; after a suspension exactly one coalesced incremental job per overdue group, spread by `WAKE_SPREAD_MS` (its persisted floor predates the suspension, so the whole gap is re-read with overlap in one poll instead of one poll per missed interval), plus one bounded overlap reconciliation (gap + overlap, capped at the capability window) for groups that were not otherwise due. Dispatched queued runs carry a dispatch lease (`import_runs.lease_token = dispatched:<group>`) so they are not re-dispatched before the lease expires. Fairness: never-polled groups first, then oldest attempt, at most `2 x MAX_CONCURRENT_POLLS` dispatches per tick; `retry_after_until` is respected; nothing is dispatched while storage is critical. |
| `outbox.dispatch` | every `OUTBOX_INTERVAL_MS` | Marks `outbox.dispatched_at` in sequence order per tenant and `NOTIFY journal_dispatched`. |
| `backups.due` | cron `BACKUP_CRON` (default `0 3 * * *`, UTC) | Runs `BACKUP_COMMAND` (path + args, never a shell string) when configured, skipped (visible in `worker_job_log`) otherwise or when storage is critical. |
| `retention.cleanup` | cron `RETENTION_CRON` (default hourly) | Deletes `worker_job_log` older than 30 days and resolved dead letters older than 90 days. Never the journal, evidence or import coverage. |
| heartbeat | every `HEARTBEAT_MS` | Upserts `worker_heartbeat` (instance, version, wall/monotonic clocks, suspension gap, storage state and volumes, queues) for the diagnostics health card. |
| storage check | every `STORAGE_CHECK_MS` | `statfs` on `STORAGE_PATHS`; thresholds from `storage_thresholds` (first row) or defaults warn < max(10 %, 5 GiB), critical < max(2 %, 1 GiB). Critical pauses the next fetch inside running jobs (`import_runs.state = paused`, `next_action = free_disk_space`, `capability_health.status = paused`) and the scheduler; cursors are retained and runs resume automatically. |

Run execution (`apps/worker/src/sync.ts`): the connection secret is decrypted with the installation data key (`DATA_KEY_FILE` / `SECRETS_DIR/data.key`, the `@blackbox/auth` AES-256-GCM codec with AAD `tenant_id|connection_secret|key_version`, wrapped by `packages/connectors/src/secrets.ts`); the adapter is built from `connections.config_json` (`shop_domain`, optional `base_url` for the fixture, `page_size`); per page one tenant transaction ingests observations, updates `import_runs` counters (`requested` from exact provider counts, `loaded` logical records, `committed` distinct records with new entries, `duplicates`, `conflicts`, `rejected`, `applied` from `engine_checkpoints`, `totals_known` only for backfills with exact counts) and `capability_health` (`last_attempt_at`, cursors, `last_journal_commit_at`/`last_new_event_at` only when entries were committed); completion sets `last_successful_check_at` (never on failure/partial), coverage, `next_check_at` with jitter and `next_reconciliation_at`. Credential checks update attempts, grants and connection status but never a successful sync. Account identity: `checkCredentials()` returns the immutable shop/account gid; a mismatch with `connections.account_ref` sets `reauthorization_required`, fails runs non-retryably and leaves cursors untouched (a different account needs a new connection).

Logs follow `packages/contracts/log-record.json` (allowlist, 512-char clipping, 16 KiB cap, JSON to stderr via pino) with `tenant_id`/`connection_id`/`run_id`/`capability_id`/`attempt`, `journal.batch_committed` after COMMIT with `committed_cursor`, `source.run_failed` with `error_code`/`retryable`/`next_retry_at`, `worker.suspension_detected`, `storage.state_changed`. No tokens, payloads or customer ids are logged (asserted in tests).

Environment: `DATABASE_URL_WORKER` (or `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD_FILE` as in the Compose release), `DATA_KEY_FILE` or `SECRETS_DIR`, `LOGS_DIR`/`LOG_DIR` (shared log files `records-*-worker.jsonl`), `FENCE_DIR` (`writers.paused.json` idles the scheduler and queued jobs), `WORKER_INSTANCE_ID`, `SERVICE_VERSION`, `SCHEDULER_TICK_MS` (5000), `MAX_CONCURRENT_POLLS` (2), `WAKE_SPREAD_MS` (15000), `SUSPENSION_THRESHOLD_MS` (60000), `LEASE_SECONDS` (300), `MAX_PAGES_PER_JOB` (200), `EVIDENCE_DIR` (`./data/evidence`), `STORAGE_PATHS` (colon-separated), `STORAGE_CHECK_MS`, `BACKUP_COMMAND`, `BACKUP_CRON`, `RETENTION_CRON`, `OUTBOX_INTERVAL_MS`, `HEARTBEAT_MS`, `LOG_LEVEL`, `PGBOSS_SCHEMA`, `JOB_RETRY_LIMIT`. All numeric values are validated with finite bounds.

Database (`0100_worker.sql`): adds cursor/lease/backoff columns to `capability_health` and counter/lease/error columns to `import_runs` (both from `0003_operations.sql`), creates `worker_dead_letters` (RLS), `worker_heartbeat`, `worker_job_log`, the `worker_enumerate` SELECT policy on `tenants` for `bb_worker`, and the `pgboss` schema.

Cases: SLICE-01 steps 2-3/6, INGEST-02/03/04/05, JOURNAL-01/02, HEALTH-01, IMPORT-02/05, TENANT-01/02, PILOT-05/06, SOURCE-01 (synthetic subset).

Cases: PILOT-05/06, INGEST-05, HEALTH-01.

The pipeline suite runs end-to-end against PostgreSQL in a container; on a heavily loaded host (this run: load average > 500 with many parallel agent stacks, ~25 ms per trivial query) it takes several minutes, so the vitest timeout is generous. Correctness, not wall time, is asserted.
