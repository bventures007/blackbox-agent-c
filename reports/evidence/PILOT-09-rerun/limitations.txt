Host is a developer Mac shared with ~40 containers of three other Blackbox projects; host load averages ranged 10–120 (1 min) during the runs, far above the contract's dedicated 4 vCPU / 8 GiB reference host. Docker Desktop VM: 8 vCPU / 9.7 GiB for every project together.
Second install (ops2) ran release 0.1.3 built from the same tree as 0.1.0 plus the fixes listed in reports/evidence/RERUN/README.md (hot-path scans, 503 backpressure, readiness memo); the archive promoted to testers is 0.1.0 build #8 of that tree.
Closed-loop runs (API and MCP) were re-measured on the 0.1.4 install after the parameter-contract fix (D22) so the summary class produces real answers; the fixed-arrival runs are from the 0.1.3 install where the summary class failed on invalid_params (its latency sample is a validation round-trip, success 0). API runs were measured first on the 0.1.3 install; the MCP runs crashed on the first attempt because of a driver defect (undici HeadersTimeoutError in the ingestion barrier read, tests/perf/smoke.mjs) and were re-run after the fix at 03:22–03:46 UTC. Between the attempts the api served the orphaned backlog for >40 min and was restarted (observation D21).
Engine container memory limit 1.5 GiB; the corpus (50 tenants) exceeds the 1,024 MiB steady target by design of the bounded working set (evictions observed), so memory targets are reported, not met.
Restore timing is the wall time of the isolated restore command (200 s incl. pg_restore and container start), not a separate query-ready probe. Rebuild timing (196 s) was measured on the shared host.
Latency figures include client-side queueing in the driver (scheduled arrival to completion) as the contract requires.
