Shared developer Mac (Apple M3, 8 cores, 24 GiB; Docker Desktop VM 8 vCPU / 9.7 GiB shared with 11-17 containers of other projects), not the contract's dedicated 4 vCPU / 8 GiB reference host; host 1-min load averages are recorded before/during/after every run (perf-sampler.sh, smoke-protocol.txt). During the run-1 protocol the host load rose to 90-240 (Spotlight/file-provider indexing and other processes next to the Docker VM, see top snapshot in the README), so run 1 is a saturated-host measurement.
Engine memory in the verdict is docker stats cgroup memory (includes the page cache of snapshots/logs the engine writes), the comparator used since the first measurement; the engine's own VmRSS (sampler, /proc/1/status) is reported next to it.
Ingestion runs at 7 observations/s x 3 journal entries = 21 entries/s (contract: 20 journal entries/s); earlier attempts used 20 observations/s = 60 entries/s, i.e. three times the contract rate.
Cold reads use as_of_recorded cutoffs over the ten minutes before each run start; in run 1 (api-closed, started 4 min after corpus generation ended) 111 cold requests asked for a cutoff before the sampled order existed and the engine answered 404 invalid_params ("not known in this tenant"), which the driver counts as failures although they are correct historical answers; later runs have no such cutoffs.
Restore time is measured from the restore command start until an authorized owner query of the restored install answered 200/current (107 s); the restored install's new owner key is shown only at the end of the command, so the probe cannot start earlier; operator input 0 s.
The corpus is the generator's deterministic seed-42 output (552,798 entries at generation); the owner workspace grew by the protocol's own ingestion (~12,600 entries per 600 s run plus the 1,002-entry restart tail); the 50 corpus tenants queried by the drivers are unchanged between run 1 and run 2.
Run 2 repeats the protocol on the same install after the ADR-0008 fix (0000_roles.sql LEAKPROOF flag applied through the install's own bootstrap file); the api/worker/engine/backup images are the unchanged 0.1.1-perf images built from commit 9b64931 because the fix is SQL executed by the wrapper, not image code. Run 2 starts after a ./blackbox down/up lifecycle restart (engine loaded from snapshots) whereas run 1 started directly after the live corpus apply (engine RSS 1,000 MiB at start); both starting states are recorded in the smoke-protocol.txt engine lines.
Synthetic evidence for the restore test is the raw replay payload store written by the ingestion (~63 MiB), not a 250 MiB evidence set.
Latency figures include client-side queueing in the driver (scheduled arrival to completion) as the contract requires; MCP figures include the stdio bridge (official SDK client, one bridge process per principal).
