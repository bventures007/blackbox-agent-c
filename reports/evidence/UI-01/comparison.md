# UI-01 — reference design ↔ pilot UI comparison (re-run 2026-11-02)

Scope: every view and dialog of the pilot web app (`apps/web`) and the landing page (`apps/landing`), EN and DE, desktop 1440×1000 and mobile 390×844, compared with the 67 reference captures in `reference/screenshots/` (58 desktop, 9 mobile). The reference is the static German prototype; the pilot is English by default with complete German.

## Method and its limits (honest)

- Installation under test: the fresh-folder install of archive 0.1.0 build #8 (sha256 922d6517…) in `~/blackbox-pilot-fresh` for the verdicts, then re-captured on the final build #9 (sha256 2e665fe3…, after the D22/D23 fixes) in `~/blackbox-pilot-fresh2` — the screens under `reports/evidence/UI-01/screens/` and `capture/` are the build-#9 captures (126 screens, 34 with controls inside horizontally scrolling tables, 4/4 focus-trap checks; `capture-run-b.txt`), the build-#8 capture is kept under `capture-build8/`; the only UI difference between the two builds is the set of question parameter fields (D22: the typed form now offers exactly the engine's parameters plus as_of), which does not change any verdict row. Compose project `blackbox-agent-c`, `http://127.0.0.1:19180`, populated by the Playwright suite (GOLDEN demo through the real ingestion path, replay and bank-CSV connections, review case).
- Captures: `scripts/verify/ui-capture.mjs` in real Chromium 1248 (Playwright, headless): 126 screens = 31 desktop + 32 mobile per locale under `reports/evidence/UI-01/capture/<locale>/<width>/` (full page unless a dialog is open), plus `capture-report.json` with per-screen clipped-control checks and the keyboard/focus results below. The suite's own screenshots of the passing run 5 are under `reports/evidence/UI-01/screens/`. Landing states: `reports/evidence/DIST-01/`.
- Limitation: the owner key must not be materialised into the verifier's context, so the sign-in could not be typed into the Claude built-in browser pane; the authenticated screens were therefore captured by Playwright-driven Chromium (the same engine, reading the key from the 0600 file) and compared by the verifier image by image for the main views (recorder, sources, answer, journal, system & diagnostics, settings, agents, mobile recorder) and by assertion + capture report for the rest. The landing page was additionally checked by hand in the built-in browser pane (EN/DE, real download clicks, see DIST-01).
- The agent key shown once in the UI was masked in the DOM before its capture (`47-agent-key-shown`); no capture contains a key.

## What matches the reference

Palette, type and chrome (`packages/ui/styles/prototype.css` is the unchanged prototype stylesheet); the shell (dark sidebar with the same navigation order, workspace block, "Ask a question", brand callout, landing link; top bar with breadcrumb, local/preview tag, runtime status, language switch); the Recorder (heading, four stat cards, five parallel tracks with ruler and controls, the two lower panels, footer note); Sources (jump links, category sections, cards with glyph/state pill/capabilities/limitations, connect dialogs with the three-step summary); Questions (labeled search panel, six group cards × four questions, expandable question, answer block with eyebrow, headline, calculation row, citation chips, data status); Journal (filter toolbar, ledger columns, track tags, entry drawer with typed payload/evidence/links, empty state); Agents & MCP (grant explanation, key table, three-step flow, client choice, stdio config, tool list); mobile (single column, hamburger drawer with `aria-expanded`, horizontally scrolling tables, full-width dialogs/drawers).

## Fixed during this verification (real defects, see `reports/evidence/RERUN/README.md`)

- Focus trap re-ran on every poll re-render (dialog scroll reset and re-focus every 5 s); fixed in `useFocusTrap`.
- Long dialogs on narrow screens: the import-plan dialog's primary button could not be reached/tapped at 390 px (actions slot with a fixed actions row; dialogs anchored to the top on narrow screens). Verified by Playwright run 5 (68/68) and the capture pass.
- Worker health card now reads the worker's own heartbeat (liveness) instead of inferring from work tables; backups surface reads the wrapper/scheduler status file.

## Orchestrator spot-check (2026-11-03)

Independently of the verifier's per-capture table, the orchestrating agent compared four pairs image-to-image (reference capture vs. real-browser screenshot of the build-#9 install): 08-recorder, 22-answer-inventory, 46-agents and 02-landing-hero/01-landing.

- Matches: green/cream palette, dark sidebar with workspace card and the same navigation order, five-track recorder with per-track entry chips and counts, four stat cards, two-panel lower section (question shortcuts, recent activity), agents page with connection panel, copyable configuration block and tool list, landing hero with headline pair, two actions and the recorder preview.
- Deviations (all already listed above as intentional or documented): English default with locale switch; readiness badges instead of demo-assistant chips; the 24-question catalogue lives on Questions & Answers instead of below the agents page; the answer is rendered as the typed engine envelope (calculation steps, result fields, evidence, data status) inside the group card rather than the prototype's single headline sentence with three large numbers; the landing adds the release metadata card and installation guide required by the download contract; the header badge shows the measured health state ("Degraded" when backups are unconfigured) instead of the prototype's static "System ready".
