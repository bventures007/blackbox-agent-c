# PILOT-09 follow-up — engine memory and no-snapshot rebuild on the 50-tenant corpus (2026-11-03)

Targets are unchanged (benchmarks/performance-contract.json smoke profile: engine steady RSS ≤ 1,024 MiB, no-snapshot rebuild ≤ 180 s). PILOT-09 / OPS-05 stay **failed** until the full smoke protocol passes; this follow-up records bounded engine improvements and before/after measurements on the second install (`~/blackbox-pilot-ops2`, Compose project `blackbox-agent-c-ops2`, 723,780 journal entries / 54 tenants / 10,000 orders, engine `mem_limit` 1.5 GiB) on the same shared Mac (host load averages recorded in every file).

## Findings in `crates/projections` (0.1.4 tree)

1. **Per-batch full clone of the tenant state.** The left-right double buffer re-applies each batch on the retired copy, but whenever the publication had evicted (always, on this corpus: the structural budget is 512 MiB / 2 copies / 54 tenants ≈ 4.7 MiB per copy while the two large tenants need ≈112 MiB per copy — the floor is the per-entry metadata that eviction never drops) it fell back to `*st2 = (*write).clone()`: a deep clone of ≈110 MiB per 1,000-entry batch (277 clones for tenant 0 during a catch-up) → glibc heap churn and RSS far above the live heap.
2. **Per-batch checkpoint + publication during catch-up**: one fsync'd `engine_checkpoints` write, one `approx_bytes()` walk and one O(n log n) eviction per 1,000 entries.
3. **Eviction of undo logs ahead of pending corrections**: the per-batch eviction dropped the undo logs of the oldest half of resident entries; the corpus has 500 `payment.fee_booked` corrections (`supersedes_entry_id`) whose targets' undo logs were already gone when they arrived in the same catch-up → `engine.rebuild_requested` 507 times in one catch-up (engine log counters of the 0.1.4 container, `measurement-before-aborted.txt`), each rebuild building a third full copy of the tenant.
4. **Two resident copies for every tenant, idle or not**: 54 tenants × 2 copies; the structural estimate (779 MiB) and RSS (1,194 MiB after a plain snapshot load) are both dominated by the second copy and the hashbrown/allocator overhead the estimate does not count (≈1.5×).
5. `ENGINE_HOT_BUDGET_MB` is a structural estimate only; measured RSS never fed back into eviction.

## Changes (uncommitted in the working tree; the orchestrator commits)

- `crates/projections/src/engine.rs` (tail loop): lazy private write copy — a tenant with no new entries for `ENGINE_WRITE_COPY_IDLE_SECONDS` (60) releases it (one resident copy per idle tenant; the next batch clones once); single-pass catch-up with `ENGINE_CATCHUP_BATCH_SIZE` (5000) batches and publication/checkpoint at most every `ENGINE_CATCHUP_PUBLISH_MS` (10 s) or when the tail is exhausted (`/health` exposes the write copy's `catching_up_cursor`); the retired copy replays the batch and runs the same deterministic eviction instead of being cloned (fingerprint check + clone fallback on divergence); after a multi-batch publication the retired copy is dropped instead of cloned; admin rebuild drops the write copy (no third copy); `malloc_trim` after drops/evictions/rebuilds.
- `crates/projections/src/evict.rs` + `lib.rs` + `crates/domain/src/state.rs` (`evictable_bytes`): the structural budget now applies to the evictable part of a state (history locators + undo logs) and is shared by tenant size (`Registry::tenant_budget_for`, never below 1 MiB, halved while the private copy is resident). Before, the whole estimate was compared with an equal share of 512 MiB / 2 / 54 ≈ 4.7 MiB, below the unevictable floor of the two large tenants (≈112 MiB each), so every history locator was evicted at every publication and every hot lookup of those tenants turned into a PostgreSQL entity read (`pg_stat_activity` during the smoke runs: 12 concurrent `bb_engine` entity SELECTs, PostgreSQL at 450–630 % CPU). Found after the first protocol re-runs; measured in the third run below.
- v4 of the budget (after attempt 3, below): the evictable total is bounded by the RSS target minus the measured floor of all tenants (× 5/8, ≥ 32 MiB) and an eviction pass needs an excess above target/8 (≤ 4 MiB); per-tenant `evictable_bytes` is tracked and reported in `/health`.
- `crates/projections/src/evict.rs`: `evict_history_to_budget` (history locators only) used while catching up or rebuilding; undo logs are evicted only once the tenant is caught up, so pending journal corrections never meet an evicted target (no rebuild storm, no double count).
- `crates/projections/src/lib.rs`, `apps/engine/src/main.rs`: `ENGINE_RSS_TARGET_MB` (default 1024; 0 = off): measured RSS above the target drops idle write copies at once and halves the structural budget at the next publication (`rss_evictions`); health reports `rss_target_bytes`, `rss_over_target`, `write_copy_resident`, `write_copies_dropped/cloned`, `catching_up_cursor`; `approx_resident_bytes` counts one copy for idle tenants.
- `crates/projections/src/mem.rs` (RSS + `malloc_trim`; `apps/engine/src/rss.rs` re-exports), `crates/projections/Cargo.toml` (+libc on linux/macos), `Cargo.lock`.
- `infra/compose/docker-compose.yml`: engine `MALLOC_ARENA_MAX=2` (`BLACKBOX_ENGINE_MALLOC_ARENA_MAX`) and `ENGINE_RSS_TARGET_MB` (`BLACKBOX_ENGINE_RSS_TARGET_MB`, 1024).
- `docs/engine.md`: catch-up/idle-copy section, memory accounting, environment table.
- `packages/auth/src/service.ts` (API hot path, found during the smoke re-run): the agent-key argon2id verification (64 MiB, t=3, ≈100–200 ms CPU) was re-run every 5 s per key (`VERIFY_CACHE_MS`) and by every concurrent miss in parallel; with 20 agent keys at 40 req/s the api container saturated four cores (`docker stats` 272–428 % CPU) while the engine idled at 9–17 %. The cache now keeps the key-hash → credential-id result for 10 min and concurrent misses share one in-flight verification; the credential/principal rows (status, expiry) are still re-read on every request, so revocation stays immediate (auth.test.ts LOCAL-04 and mcp.test.ts MCP-05 "stops serving within 5 s after revocation" pass: 16/16). Not yet in the images measured below.
- `scripts/verify/ops2-engine-followup.sh`: the before/after protocol (restart → warm-up 300 hot lookups → idle → no-snapshot rebuild with `engine_snapshots` cleared as `bb_engine` → idle → warm-up; RSS from `/proc/1/status`, health from the API card every 2 s as in `ops2-restart-rebuild.sh`).

Tests: `ENGINE_BINARY=target/release/blackbox-engine cargo test --workspace --release -- --test-threads=2` → all crates pass (`cargo-test-workspace-release-v2.log`, exit 0: domain golden 14, golden_http 4, intents_http 1, ops_http 5 incl. restart-with-snapshot/corrupt-snapshot-rebuild, 1,000-entry unapplied tail within 30 s under concurrent ingestion, and the release-binary hot-state p95 < 200 ms sample). The first full run (`cargo-test-workspace-release.log`) failed only the latency sample (p95 282 ms, 0 errors) while the host load average was 43–51 from the concurrent cargo/docker builds; rerun alone it passed (`cargo-test-load-sample-rerun.log`).
